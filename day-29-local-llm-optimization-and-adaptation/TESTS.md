# Сценарии тестирования LLM Parameter Lab

Каждый сценарий показывает **один изолированный эффект**: меняем только один параметр, остальные фиксируем. Текст для всех тестов — **"Запись к мастеру"** (кнопка в интерфейсе), если не указано иное.

---

## Тест 1: Влияние квантования

**Гипотеза:** Q2-квантование деградирует качество структурированного вывода — JSON ломается или содержит галлюцинации.

| | Колонка A | Колонка B |
|---|---|---|
| Модель | `qwen2.5:7b` (Q4_K_M) | `qwen2.5:7b-instruct-q2_K` |
| Temperature | 0.1 | 0.1 |
| num_ctx | 4096 | 4096 |
| max_tokens | 512 | 512 |
| System Prompt | Детальный (с JSON-схемой) | Детальный (с JSON-схемой) |

**Ожидаемый результат:**
- A → валидный JSON, поля нормализованы (телефон в формате +7...)
- B → возможны: изменение схемы, выдуманные поля, невалидный JSON, мусор после JSON

---

## Тест 2: Влияние temperature

**Гипотеза:** Высокая температура делает JSON-экстракцию нестабильной — структура меняется от запуска к запуску, появляются случайные поля.

| | Колонка A | Колонка B | Колонка C |
|---|---|---|---|
| Модель | `qwen2.5:7b` | `qwen2.5:7b` | `qwen2.5:7b` |
| Temperature | **0.0** | **0.7** | **1.5** |
| num_ctx | 4096 | 4096 | 4096 |
| max_tokens | 512 | 512 | 512 |
| System Prompt | Простой (без схемы) | Простой (без схемы) | Простой (без схемы) |

**Ожидаемый результат:**
- A → идентичный JSON при каждом запуске
- B → незначительные вариации формата
- C → разная структура при каждом запуске, возможен нежелательный текст вокруг JSON

**Совет:** запустите каждую колонку 2–3 раза и сравните — при `temp=0` результат всегда одинаковый.

---

## Тест 3: Влияние системного промпта

**Гипотеза:** Детальный промпт с JSON-схемой кардинально улучшает качество — даже слабая модель начинает возвращать правильную структуру.

| | Колонка A | Колонка B | Колонка C |
|---|---|---|---|
| Модель | `qwen2.5:7b` | `qwen2.5:7b` | `qwen2.5:7b` |
| Temperature | 0.3 | 0.3 | 0.3 |
| num_ctx | 4096 | 4096 | 4096 |
| max_tokens | 512 | 512 | 512 |
| System Prompt | **Без промпта** | **Простой** | **Детальный (с JSON-схемой)** |

**Ожидаемый результат:**
- A → свободный ответ, возможно с объяснениями на русском, не JSON
- B → попытка JSON, но без схемы — поля произвольные
- C → строго по схеме, телефон нормализован, дата в YYYY-MM-DD

## Тест 4: Влияние контекстного окна (num_ctx)

**Гипотеза:** При маленьком контекстном окне модель "не видит" конец длинного текста — теряет данные.

**Текст:** вручную вставьте в поле длинный текст (повторите текст "Обращения в поддержку" 5–6 раз подряд, чтобы он был ~2000 символов).

| | Колонка A | Колонка B |
|---|---|---|
| Модель | `qwen2.5:7b` | `qwen2.5:7b` |
| Temperature | 0.1 | 0.1 |
| **num_ctx** | **512** | **4096** |
| max_tokens | 512 | 512 |
| System Prompt | Детальный (с JSON-схемой) | Детальный (с JSON-схемой) |

**Ожидаемый результат:**
- A → данные из конца текста пропущены или заменены `null`; возможен обрезанный промпт
- B → все поля заполнены корректно

## Тест 5: Q2 + высокая temperature + без промпта = полная деградация

**Гипотеза:** Комбинация деградирующих факторов даёт наглядный провал — модель перестаёт следовать задаче.

| | Колонка A (эталон) | Колонка B (деградация) |
|---|---|---|
| Модель | `qwen2.5:7b` | `qwen2.5:7b-instruct-q2_K` |
| Temperature | **0.1** | **1.3** |
| num_ctx | 4096 | 4096 |
| max_tokens | 512 | 512 |
| System Prompt | Детальный (с JSON-схемой) | **Без промпта** |

**Ожидаемый результат:**
- A → эталонный чистый JSON
- B → хаотичный ответ: смесь языков, неверные данные, невалидная структура

## Тест 6: GigaChat vs Ollama (при наличии ключа)

**Гипотеза:** Облачная модель (GigaChat-Pro) на том же задании показывает лучшее качество нормализации данных, чем локальная 7b.

| | Колонка A | Колонка B |
|---|---|---|
| Модель | `GigaChat-Pro` | `qwen2.5:7b` |
| Temperature | 0.1 | 0.1 |
| num_ctx | N/A | 4096 |
| max_tokens | 512 | 512 |
| System Prompt | Детальный (с JSON-схемой) | Детальный (с JSON-схемой) |

**На что обратить внимание:**
- Скорость ответа (GigaChat быстрее из-за серверного GPU, но зависит от сети)
- Точность нормализации телефона (+7XXXXXXXXXX)
- Формат даты (YYYY-MM-DD)
- Токены в ответе — GigaChat считает по-другому

**Текст:** "Обращение в поддержку" — в нём email + телефон в формате `8 (495) 000-11-22`, что требует нормализации.

## Тест 7: Chain-of-Thought vs прямая экстракция

**Гипотеза:** Chain-of-Thought улучшает рассуждение, но ломает прямой парсинг JSON — в сыром ответе появляется текст до JSON.

| | Колонка A | Колонка B |
|---|---|---|
| Модель | `qwen2.5:7b` | `qwen2.5:7b` |
| Temperature | 0.1 | 0.1 |
| num_ctx | 4096 | 4096 |
| max_tokens | 512 | 512 |
| System Prompt | **Детальный (с JSON-схемой)** | **Chain-of-Thought** |

**Ожидаемый результат:**
- A → прямой JSON без лишнего текста
- B → текст "Найдено: ...", затем JSON — таб "Сырой ответ" покажет разницу; парсер всё равно извлечёт JSON из тела ответа

---

## Итоговая матрица эффектов

| Параметр | Малое значение | Большое значение |
|---|---|---|
| Квантование (bits) | Деградация, галлюцинации | Точное следование инструкциям |
| temperature | Детерминированный JSON | Случайная структура |
| num_ctx | Потеря данных из длинного текста | Полный охват контекста |
| max_tokens | Обрезанный ответ | Полный ответ |
| System Prompt | Свободный ответ | Строгая схема |
